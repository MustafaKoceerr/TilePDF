# Phase 13: XFA Forms — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.

**Goal:** Dynamic XFA forms, the ones that show only "Please wait…" in most readers, open laid out. They can be filled in, and are saved with their data.

**Architecture:**
- **Loading.** A form document whose type is XFA gets `xfa_disabled = 0`; `FPDF_LoadXFA` runs right after the form environment is made. PDFium then lays out the pages from the template, and `FPDF_FFLDraw`, which we already call, draws them.
  - Verified: a dynamic XFA form needs `<dynamicRender>required</dynamicRender>` in its config packet, as real ones have.
- **Interaction.** XFA widgets aren't PDF annotations. So on an XFA document a tap goes to PDFium (`FORM_OnMouseMove/LButtonDown/LButtonUp`), and every page redraws.
  - PDFium tells a text field took focus through `FFI_DisplayCaret`. The tap then returns the field's text (`FORM_GetFocusedText`), and the reader opens its text dialog.
  - The new text is written with `FORM_SelectAllText` / `FORM_ReplaceSelection` / `FORM_ForceToKillFocus`.
- **The draft keeps edits, not values.** XFA values can't be read by name, so the draft keeps the edits in order: a tap at (page, x, y), with the text written there, if any.
  - The engine is deterministic: replaying the same edits on the same file gives the same form. They are replayed on open (the reader's document) and when saving (the saver's document).
  - The save checks each text edit by tapping the same point in the saved file and reading the focused text.
  - Room v9 adds `annotation_drafts.xfaEdits` (JSON, default `[]`).
- **If the page count changes** (a dynamic form adding a page), the reader reopens the document. The open replays the pending edits.
- **Full-XFA pages aren't PDF pages.** Annotation tools, recognising text and the no-text chip are off for them. Search finds nothing there.

**Tech Stack:** PDFium XFA (cppgc, V8), JNI form-fill callbacks, Room v9, Kotlin, Compose.

**Spec:** the roadmap, phase 13. It is stacked on phase 12.

## Global Constraints
- **Offline.** XFA's network callbacks stay unset, so they fail.
- **AcroForm and plain documents behave exactly as before.**
- **A failure falls back.** An XFA form PDFium can't lay out falls back to the PDF pages, as today.

## Review Focus
- **A tap on a non-text widget** (check box, or empty space): no dialog. The tap is still kept, since it may have toggled something.
- **The reader closes after edits.** Saving replays them and the file holds the data: reopening without a draft shows the text.
- **A full-XFA document never takes annotations,** which would make every save fail.
- **Hybrid (XFA foreground) forms** keep their AcroForm widgets and the existing fill path.

### Task 1: Load and draw XFA (native)
- JNI:
  - `xfa_disabled` from the form type, and `FPDF_LoadXFA`;
  - `nativeIsXfa(doc)`, true for full XFA;
  - `FFI_DisplayCaret`, which records whether a caret shows;
  - `nativeFormTap(doc, page, x, y): String?`: the focused text when a text field took focus, else null;
  - `nativeFormReplaceText(doc, page, text): Boolean`.
- `tools/generate_test_pdfs.py`: `xfa.pdf`, with a config, a text field "name" and a check box.
- Test (device): `PdfiumXfaTest`:
  - laid out instead of the placeholder;
  - a tap on "name" returns ""; writing "Ada" draws ink there;
  - a tap on the caption returns null;
  - saved and reopened, a tap on "name" returns "Ada".

### Task 2: XFA edits in the draft (JVM)
- Model: `XfaEdit(pageIndex, at: PdfPoint, text: String?)`, plus `AnnotationDraft.xfaEdits`.
- `FillableForm`:
  - `isXfa()`;
  - `xfaTap(pageIndex, at): String?`;
  - `xfaWrite(pageIndex, text)`;
  - and `suspend fun FillableForm.replay(edits: List<XfaEdit>)`, a tap and then a write when there's text.
- `AnnotationCodec`: XFA edits as JSON. Room v9: the `xfaEdits` column with an auto-migration; schema `9.json`.
- `AnnotationRepository.addXfaEdit(uri, edit)` makes the draft dirty. `markSaved` drops the first n saved edits, keeping any made since. `moveTo` keeps the unsaved ones.
- `AnnotationSaver`:
  - `write` and `export` replay `draft.xfaEdits`;
  - `holdsExactly` checks the last text written at each point, by `xfaTap` on the saved file.
- Tests:
  - `ReplayTest`: taps, then writes, in order;
  - `AnnotationCodecTest`: XFA edits round trip;
  - `OfflineAnnotationRepositoryTest`: add, mark saved, keep newer;
  - `AnnotationSaverTest`: replayed and checked; a lost value fails the save.
  - Device: `TilePdfDatabaseMigrationTest.migrate8To9`.

### Task 3: The reader
- `ReaderViewModel`:
  - knows `documentIsXfa` on open, and replays pending edits there;
  - a tap on an XFA document goes to `xfaTap` and is kept as an edit; a returned text opens the text dialog. Submitting writes and keeps the text edit, and every page redraws;
  - when the page count changes, the document reopens.
  - Annotation mode, recognition and the no-text chip are disabled on full XFA.
- `ReaderScreen`:
  - the text dialog for XFA, with no field name to show, titled "Text field";
  - the pen button is hidden on XFA.
- Strings: EN and TR.

### Task 4: Docs and checks
- README: XFA supported (dynamic forms laid out, filled and saved); annotations and OCR aren't available on full-XFA pages.
- The full suite, lint, release and permissions; `PdfiumXfaTest` and the migration test on the emulator.
- By hand: open `xfa.pdf`, type a name, leave, reopen, and the name is there.
